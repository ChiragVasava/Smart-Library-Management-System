# Smart Library Management System — Playwright Testing Architecture

## 1. Architectural Overview

This document illustrates the end-to-end architecture and data flow connecting **TestForge AI**, the generated **Playwright Test Suite**, the **Web Presentation Layer**, and the underlying **Smart Library Domain Logic**.

The goal of this architecture is to provide a clean, decoupled web interface over an existing Python domain model so that automated end-to-end browser tests generated by TestForge AI can execute against real application logic without requiring rewrites or artificial mocking.

## 3. Pre-Existing vs. Newly Added Components

### A. Pre-Existing Components (Preserved Intact)
The following components formed the original Smart Library codebase and were **strictly preserved without destructive changes**:

1. **`library_manager.py`**: The core orchestrator. Coordinates lending transactions, overdue fine calculations, returns, and logging.
2. **`models.py`**: Dataclasses and object models (`Book`, `Loan`, `Member`, `Student`, `RegularMember`, `PremiumMember`, `BookStatus`, `MembershipType`).
3. **`inventory.py`**: Manages the catalog dictionary, lookup operations, stock modifications, and check-in loops.
4. **`membership.py`**: Manages member accounts, tier-based borrow limits (Regular: 3, Student: 5, Premium: 10), and active loan validation.
5. **`payment.py`**: Strategy-based payment processing with external gateway simulation and retries.
6. **`notification.py`**: Async notification dispatching for email, SMS, and push channels.
7. **`decorators.py`**: Decorator logic for timing (`@timed`), authorization (`@admin_required`), and fault recovery (`@retry`).
8. **`exceptions.py`**: Custom domain exceptions (`LibraryError`, `BookNotAvailableError`, `BorrowLimitExceededError`, etc.).
9. **`logger.py`**: Context-managed logging configuration.
10. **`main.py`**: CLI runnable demonstration entry point (`python main.py`).
11. **`tests/test_sample.py`**: Reference unit test suite with 12 tests.

---

### B. Newly Added Components
To allow browser automation against the application, the following components were introduced:

1. **FastAPI Web Server (`web_app.py`)**:
   - Acts as the HTTP adapter over `LibraryManager`.
   - Exposes RESTful endpoints and page view controllers.
   - Manages user sessions via lightweight cookies (`user_email`).
   - Implements automated test state resets on login navigation and via `/api/reset`.

2. **Jinja2 Presentation Templates (`templates/`)**:
   - `base.html`: Common layout with navigation links, branding, dark-theme styles, and responsive container.
   - `login.html`: HTML form featuring input selectors `input[name="email"]`, `input[name="password"]`, and button `"Login"`.
   - `books.html`: Catalog view with greeting `"Welcome, member!"`, search input `placeholder="Search books..."`, and `.book-card` elements with `"View Details"`.
   - `book_detail.html`: Book detail view featuring heading `"The Great Gatsby"`, `"Borrow"` button, modal dialog `.confirmation-modal` with `"Confirm Borrow"`, `.toast-success` banner, and `"Return"` button.
   - `my_books.html`: Profile view rendering active loans inside `div.borrowed-book-card` containers with loan due dates.

3. **Playwright Test Suite (`playwright_tests/`)**:
   - `playwright_tests/test_borrow_book.py`: The exact end-to-end browser test generated by TestForge AI.

4. **Environment & Dependency Updates**:
   - `requirements.txt`: Updated to include `fastapi`, `uvicorn`, `jinja2`, `playwright`, and `python-multipart`.

## 5. Architectural Principles Upheld

1. **Non-Destructive Extension**:
   The web layer was added purely as an external consumer of the existing business logic. No changes were made to `library_manager.py`, `models.py`, `inventory.py`, or `membership.py`.

2. **Genuine Execution Over Mocking**:
   When the Playwright test clicks "Confirm Borrow", the request triggers real execution inside `LibraryManager.borrow_book()`. The book's status changes in inventory, a `Loan` instance is instantiated and registered, and member borrowing rules are enforced.

3. **Deterministic Repeatability**:
   Automated browser tests require clean initial conditions. The state reset hook ensures that even when the test modifies application state by borrowing a book, subsequent runs immediately restore the book to `AVAILABLE` without needing database migrations or service restarts.

4. **Dual Interface Compatibility**:
   The application now seamlessly operates as both a **CLI utility** (`python main.py`) and a **Web application** (`http://localhost:3000`), preserving all original unit tests (`pytest tests -v`).
